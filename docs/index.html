Moonward

Keep a failing dependency from taking the rest of the system down with it. Nine primitives that decide from the numbers you hand them, so a ten-second outage replays in a loop that takes no time at all.

01

Where a
request dies

Four places a request can be stopped, cheapest first. Each check is a struct you hold in your own code and a call that returns Option: a call that was never going to succeed is turned away before it costs a socket.

Is there room right now?

A count with a ceiling. It has nothing to do with time: it is how many calls are inside at this instant. Past the limit the answer is no, not later.

Refuses when held has reached limit

gate64 slots
let gate = @moonward.Gate::new(64)
if gate.enter() {
  // the call runs, then
  gate.leave()
}

How likely is this backend to work?

Not a switch. The breaker keeps ten seconds of outcomes and refuses each call with a probability that grows with the failures in that window, so a struggling backend keeps getting what it can still serve.

Refuses when a draw falls under ratio(now)

breakerwindow 10s
let b = @moonward.Breaker::new()
match b.allow(now, roll) {
  Some(p) => p.pass(now) // or p.fail(now)
  None => refused
}

Is this caller within its allowance?

Three answers to three different questions. A bucket smooths a rate and lets a burst through. A sliding window counts events in any window-long stretch. A period counts them per fixed period, which is cheaper and coarser.

Refuses when the token, the count or the quota is spent

limiters100 / s
let rate = @moonward.Bucket::new(100.0)
let quota = @moonward.Sliding::new(1000, day)
let daily = @moonward.Period::new(1000, day, align=true)
rate.take(now) // true while tokens last

Is this server hot and full?

Both, or nothing is refused. A CPU spike with nothing queued sheds nothing, and neither does a long queue on an idle CPU. The threshold is what the server has shown it can finish.

Refuses when cpu is over the threshold and calls in flight are over capacity

sheddercpu 950‰
let s = @moonward.Shedder::new()
match s.allow(now, cpu) {
  Some(t) => t.pass(now) // or t.fail()
  None => "overloaded"
}
02

The parts bin

Nine types, one policy record each where a policy makes sense. Every preset can be copied and changed with two braces: { ..sre, k: 2.0 }.

MW-01

Breaker

Refuses a growing fraction of calls as a backend fails, and eases off as it recovers. Keeps a rolling window of outcomes; never opens, never closes.

MW-02

Shedder

Refuses work only when the CPU is hot and the calls in flight are over what this server has shown it can finish.

MW-03

Bucket

A token bucket. Accrues at a rate, holds up to a burst, spends one token a call.

MW-04

Sliding

At most a quota of events in any window-long stretch. Keeps each stamp, so the count is exact.

MW-05

Period

A quota per fixed period, reset at a multiple of the period when aligned. Cheaper than a slide, coarser.

MW-06

Gate

A concurrency limit. Counts what is inside now, and does not know what time it is.

MW-07

Backoff

When to try again and how long to wait first. Five jitter strategies, each drawing from the value you pass.

MW-08

Deadline

A budget measured from the instant it started. A budget of zero never expires, so an unset timeout cannot time everything out at once.

MW-09

Window

A rolling window of buckets you define. Anything with a Default can be a bucket, and the default is what a bucket is cleared back to.

No clock read.
No dice thrown.

A breaker that reads the clock itself can only be tested by waiting, and one that draws its own numbers cannot be tested at all. Here the time is a number you pass and the roll is a number you draw, so an hour of traffic is a loop over now.
